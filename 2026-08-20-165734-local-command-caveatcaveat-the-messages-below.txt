● It doesn't handle them — it skips them, deliberately.

  InboxTables.php:214 filters the selection to attachment_count === 1. Anything
  else (zero attachments, or several) is dropped before the job is dispatched,
  counted into $skipped at line 175, and reported back in the notification body
  at line 200: "N message(s) ignoré(s) : pièce jointe absente ou multiple." If
  every selected message is multi-attachment, you get "Aucun message analysable"
  and nothing is queued.

  Those messages are left untouched in the mailbox — no draft, no deletion. You
  handle them the way you do today: the "Voir" action (visible precisely when
  attachment_count !== 1, line 65) opens InboxInfolist, which builds one
  clickable action per attachment, each opening its own form and creating its
  own courrier. Note that flow never deletes the message — IncomingMailHandler
  only deletes when $attachmentCount === 1 — so a multi-attachment message has
  to be cleared with the bulk delete once you've processed it.

  I gated it that way to match the existing "Traiter" action, and because
  nothing tells the model which of several files is the courrier. Analysing all
  of them blindly would turn annexes into separate courriers, each consuming its
  own reference number — and for CPAS, its own slot in the sequential
  numbering.

  If your MFP does send multi-attachment mail regularly, there are two sensible
  extensions, and which is right depends on what those emails actually contain:

  - Several distinct courriers in one email (the copier batched separate scans)
    → one draft per attachment. Easy: analysableMessages() already maps to
    ['uid', 'index', ...], so it just stops filtering and emits one entry per
    index; the job needs to delete the IMAP message only after the last index of
    that uid.
  - One courrier plus annexes (letter + supporting documents) → one draft,
    analysed from the first attachment, with every attachment stored on it.
    IncomingMail::attachments() is already a hasMany, so the model supports it;
    the form's preview column would need to show more than attachments->first().

  Tell me which matches your mail and I'll build it — or if it's genuinely both,
  the analysis could stay skipped and I'd add a per-message choice instead.

  Having said that, my recommendation doesn't change, now for real reasons
  rather than a wrong one:

  Why retrieval still beats fine-tuning here

  - The task is memorization-shaped — this sender, writing about this topic, 
    goes to this person. That's what an index does natively and what a fine-tune
    does expensively and opaquely.
  - Your labels move. 275 recipients, staff changing jobs; a fine-tune freezes
    the mapping at training time and needs periodic retraining. Retrieval
    self-updates — and your new draft flow means every validated courrier is 
    fresh labeled data the moment the clerk clicks Valider.
  - 45% of the history has no routing at all. Fine-tuned on it, "no recipient"
    becomes a legitimate prediction. In retrieval those rows are simply never
    returned as neighbours.
  - The human is verifying a draft, not trusting it. Retrieval can say "4 of the
    5 most similar past courriers went to Mme X" — a clerk can judge that in a
    second. A fine-tune gives a name and no reason.

  Fine-tuning would likely beat naive prompting. It just costs more and gives
  you less, on a task whose whole difficulty is recall.

  What I'd actually build, in order

  Start with no embeddings at all. Meilisearch already stores content, sender,
  recipients, services, department and mail_date_timestamp for these documents —
  MeiliIndexer::createDocument() puts them there. So v1 is: search the index
  with the new letter's OCR text, filter on department, take the top ~30 hits,
  tally their recipient/service ids weighted by rank and recency, boost
  same-sender hits. Suggest the top 5. That is one repository class and zero new
  infrastructure.
